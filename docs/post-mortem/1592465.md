# AB#1592465 — `auro component <name>` CLI Command Postmortem

**Branch:** `feat/component-lookup` → `jbaker/AITooling`
**PR:** [#298](https://github.com/AlaskaAirlines/auro-cli/pull/298)
**Scope:** New `auro component <name>` command — `src/commands/component.ts` + registration in `src/index.ts` + README. Fetches a single component's published Custom Elements Manifest (`custom-elements.json`) from unpkg and prints its API (attributes, slots, events, CSS parts) plus an install snippet; supports `--tag <version>` and `--json`. 3 commits. Part of the Auro AI-readiness initiative.

## Symptoms → Lesson

| If you see... | This doc says... |
|---|---|
| `auro component <name>` lists internal base classes as if they were public components | The first cut filtered CEM declarations by `customElement`, which matches every custom-element declaration — including internal base classes that aren't shipped elements. Filter to real published elements only. Fixed in `c5f00dd0`. |
| Three related AI-readiness commands (`context`, `cem`, `component`) shipped as three separate PRs | They form one feature that must **release together**. Because auro-cli uses semantic-release, three merged PRs cut three versions and expose a half-shipped feature in between. They should have been one PR. |
| `auro component <realComponent>` returns a clean "not found" | Coverage is manifest-limited — only components that publish a CEM (~6 today) return data. Not a bug; broaden CEM coverage instead. |

## 1. What shipped

A per-component API lookup — the highest-value piece for *active* AI use. An assistant mid-task (or a human at the shell) runs `auro component auro-input --json` and gets the component's real API instead of guessing. It reads the same machine-readable CEM the aggregate (`auro cem`) and docs pipeline already produce, so it introduces no new data source and stays current by construction: it reads the live published manifest at call time, reflecting the latest version (or a pinned `--tag`).

## 2. What the review caught — internal base classes leaked into output

**Root cause.** The initial implementation (`21ee97e6`) treated every CEM declaration with `kind: "class"` and a `customElement` flag as a public component. Auro's manifests also describe internal base classes (shared superclasses that components extend). Those matched the filter, so the lookup could print declarations that aren't installable elements — misleading for exactly the AI consumers this command is meant to help.

**The fix (`c5f00dd0` — "real elements only, richer output").** Narrowed the filter to declarations that correspond to actually-published custom elements (a real `tagName`), and enriched the output at the same time. Verified against a live manifest before submission.

## 3. Process — the release-together scoping miss

This was opened as an independent PR alongside `auro context` (#296) and `auro cem` (#297), with #296→#297 stacked. In hindsight all three are one AI-readiness feature that needed to version and publish as a single release. **Lesson for next time: changes that must release together belong in one PR.** Reserve stacked/separate PRs for genuinely independent releases.

## 4. Follow-ups

- **Broaden CEM coverage** to all existing components so the lookup works library-wide (tracked separately).
- The doc-style artifacts (`llms.txt`, `auro context`) should eventually be **generated from the aggregate CEM** (AB#1593488) so they can't drift from what this command reports.
